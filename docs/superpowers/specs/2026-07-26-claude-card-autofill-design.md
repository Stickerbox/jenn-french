# Claude card autofill — design

Date: 2026-07-26

## Problem

Authoring a card means filling ten fields by hand. Five of them — hint,
grammar, Québec pronunciation, tip, idiom — are supporting material that
follows from the three the teacher actually decides: the English phrase, the
French phrase, and the subject. Writing them out every day is the slow part of
making a card, and it is the part where a draft to react to beats a blank
field.

## Goal

Turn card authoring into two stages. The teacher writes the three fields that
define the card and presses Generate; Claude drafts the five supporting fields;
the full front/back editor then appears with everything in place, ready to edit
and save.

## Scope

New:

- `lib/card-ai.ts` — Anthropic client, prompt, and the structured-output call
- `lib/card-suggestions.ts` — the pure `applySuggestion` function
- `components/InlineMarkup.tsx` — renders `**bold**`, `*italic*`, `` `code` ``
- `app/ai-actions.ts` — the server action, behind the teacher session gate
- `tests/lib/card-suggestions.test.ts`, `tests/lib/inline-markup.test.ts`

Changed:

- `components/admin/CardEditor.tsx` — two-stage flow, Generate button, request state
- `components/Flashcard.tsx` — renders inline markup; pronunciation markup fixed
- `components/card-styles.ts` — the mono chip class moves here to be shared
- `package.json` — adds `@anthropic-ai/sdk`
- `../Winery/WEBSITE_TEMPLATE.md` — `ANTHROPIC_API_KEY` row in the env var table

Unchanged:

- The `CardInput` type and both upsert server actions
- The Prisma schema — generated text is stored exactly like hand-typed text
- The Groups list, New group form, and Existing overrides list

Both `/admin` and `/admin/[slug]` get the flow. They author the same kind of
card through the same component, so a Generate step on one and not the other
would be an inconsistency with nothing behind it.

## The two stages

```
COMPOSE                              EDITING
+---------------------------+        Date * [ 2026-07-26 ]
| English phrase            |
| French phrase             |        FRONT   +--------------------+
| Subject                   |   ->           | date      (subject)|
+---------------------------+                | usage              |
        [ Generate ]                         | SAY IT IN FRENCH * |
             |                               | english prompt     |
             v                               | hint               |
        [ (spinner) ]                        +--------------------+
                                     BACK    +--------------------+
                                             | ... grammar        |
                                             | ... pronunciation  |
                                             | ... tip / idiom    |
                                             +--------------------+
                                                  [ Save card ]
```

**Compose.** Three fields, labelled and stacked: English phrase, French phrase,
Subject. No date field and no card panels yet. The Generate button sits beneath
them and is disabled until all three are non-empty.

**Generating.** The button becomes a spinner and the three fields go read-only.
Nothing else on the page changes, so the teacher can see what was sent.

**Editing.** The full front/back editor replaces the compose step, carrying the
three typed fields and the five generated ones. The date input appears here,
defaulted to the page's date. From this point the component behaves exactly as
it does today.

`usage` is generated by nobody. It is not in the compose step and Claude is
instructed not to write it, so it arrives in the editing stage blank for the
teacher to fill or leave empty.

## One generation per page load

Once the editor reaches the editing stage there is no Generate button and no
regenerate affordance. A second request for the same card cannot be issued.

Reloading the page returns it to the compose stage and allows a fresh
generation. This is the only way to regenerate, and it is a deliberate
consequence rather than a gap: it means an accidental reload after generating
but before saving loses the generated draft and costs another API call. The
alternative — persisting generated-but-unsaved state — would mean a second
storage concept for content the teacher has not yet accepted.

A card that has already been saved for the page's date skips compose entirely
and opens in the editing stage with its stored values, exactly as today.
`initialValues` being non-empty is the signal; no new query is needed, because
both pages already load the existing card.

The stage lives in component state only. Nothing about whether a card was
generated is persisted, and the database schema does not change.

## What Claude writes

| Field | Source | Rule |
| --- | --- | --- |
| englishPrompt | teacher | input to the prompt |
| frenchAnswer | teacher | input to the prompt |
| subject | teacher | input to the prompt — **Claude must not write it** |
| usage | teacher | **Claude must not write it**; left blank after generation |
| date | teacher | not sent to Claude |
| hint | Claude | one sentence, nudges toward the answer without giving it |
| examples | Claude | grammar — verb derivations, see below |
| pronunciation | Claude | Québec-specific, see below |
| tip | Claude | one practical usage or register note |
| idiom | Claude | `**expression** — meaning`, a Québécois idiom fitting the theme |

Subject and usage are excluded in the schema itself, not only in the prompt —
they are simply not fields Claude can return, so there is no way for a stray
value to reach the form.

### Grammar

Show where the conjugated forms in the French phrase come from, driven by the
subject. Infinitive in normal weight, conjugated form in bold, joined by `→`.
Close with the short rule that discriminates this tense from the one learners
confuse it with.

```
être → **j'étais**, faire → **faisait**, conduire → **conduisait**.
Repeated "would" = imparfait, not conditionnel.
```

### Québec pronunciation

Québec specifically — this is what the students are here for, and a note about
metropolitan French is worse than no note. Cover the words in the French phrase
that Québécois speakers say distinctively: vocabulary that differs from France,
consonants that shift, contractions that appear in fast speech.

Bold the word under discussion; put the phonetic rendering in a code span.

```
**Lunch** `lonch` is the everyday QC word for a packed midday meal
(France: "déjeuner/repas"). `petit` → soft "ts": `p'tsi`. `conduisait` →
the **d** before **u/i** softens toward `dz`: `con-dzui-zè`. In fast QC
speech, **j'étais** often contracts to `ch'tais`.
```

### Length

One to two sentences for hint, grammar, tip, and idiom. Pronunciation runs to
about four short sentences, roughly one per distinctive word, because that is
what the example above does — a two-sentence cap would force it to drop
material the students want. If a French phrase has only one distinctive word,
one sentence is the right answer.

## Inline markup

Claude returns `**bold**`, `*italic*`, and `` `code` `` inside the five fields.
That text is stored verbatim, so **the student card has to render it too** —
otherwise students read literal asterisks. `InlineMarkup` is shared by
`Flashcard.tsx` and the editor's card panels.

- `**text**` → semibold
- `*text*` → italic
- `` `text` `` → the mono chip: rounded, `#eef3ee` background, mono font, moss
  text — the style already on the pronunciation field today
- No nesting. An unmatched marker renders as a literal character, so a stray
  asterisk never swallows the rest of the field.

Applied to hint, examples, pronunciation, tip, and idiom. The teacher-typed
fields render as plain text.

**The `pronunciation` field's current markup is wrong for this.**
`Flashcard.tsx` wraps the entire value in one mono chip. The screenshot this
design is drawn from shows prose with chips inside it. So pronunciation becomes
a normal paragraph like grammar and tip, and the chip styling moves to code
spans within it. The chip class moves from `Flashcard.tsx` into
`card-styles.ts` so both the renderer and any remaining direct use share it.

While editing, the fields are `textarea`s and show the raw `**` and backticks.
The teacher edits the source; the rendered result is what the student sees.
There is no live-preview toggle — that is a bigger piece of UI than this
feature needs, and the markup is simple enough to read.

## Merge rule

`applySuggestion(values, suggestion)` returns a new `CardInput` with the five
generated fields set from the suggestion and every other field — date, subject,
usage, englishPrompt, frenchAnswer — carried through untouched.

There is no blanks-only logic, because generation happens exactly once, from
the compose stage, where those five fields cannot yet hold anything.

## The Claude call

```
model       claude-haiku-4-5
max_tokens  2000
output_config.format   json_schema, the five fields
```

Model choice: a short, tightly specified task returning structured output,
where a human reviews every field before it is saved. `MODEL` is a single
exported constant in `lib/card-ai.ts`; moving to `claude-sonnet-5` is a
one-line change if quality disappoints.

Three constraints specific to this model:

- **No `output_config.effort`.** Effort is Opus 4.5 and later; sending it to
  Haiku 4.5 returns a 400. Only `output_config.format` is set.
- **No thinking configuration.** Omitting `thinking` on Haiku 4.5 means no
  thinking, which suits a task this size. Switching the constant to Sonnet 5
  would make thinking adaptive-by-default and `effort` available — both would
  need revisiting then, and `max_tokens` would have to cover thinking as well
  as the JSON.
- **No prompt caching.** Haiku 4.5's minimum cacheable prefix is 4096 tokens
  and the system prompt is far shorter, so a `cache_control` marker would
  silently do nothing.

Structured outputs guarantee the response parses against the schema, so there
is no text parsing to get wrong. The schema declares the five fields as
required strings with `additionalProperties: false`. The call uses the GA
`client.messages.create` — structured outputs are not a beta feature.

## Error handling

Errors appear beneath the Generate button and return the editor to the compose
stage with the three typed fields intact.

| Cause | Message |
| --- | --- |
| `ANTHROPIC_API_KEY` unset | Claude isn't configured on this server. |
| `stop_reason === "refusal"` | Claude declined to answer this one. |
| `AuthenticationError` | Claude rejected the API key. |
| `RateLimitError` | Claude is rate limited — try again in a moment. |
| `APIError` (any other) | Claude couldn't be reached. Try again. |

Caught most-specific-first using the SDK's typed exception classes, not by
string-matching messages. `stop_reason` is checked before reading
`response.content`, because a refusal returns HTTP 200 with empty content and
indexing into it would throw.

A failed generation is the one case where the Generate button is usable twice,
since no request succeeded. The underlying error text is never returned to the
client; the messages above are the whole surface, and the teacher can act on
nothing more specific.

The `fallbacks` parameter is deliberately not used. It handles refusals from
models with elevated safety classifiers, and would move the call onto the beta
endpoint for a path that will not fire for French flashcards.

## Key handling

`ANTHROPIC_API_KEY` lives in `.env.local`, already gitignored, and is read only
inside `lib/card-ai.ts` — reachable only through a server action. It is never
prefixed `NEXT_PUBLIC_` and never referenced from a client component, so it
cannot enter the browser bundle.

`WEBSITE_TEMPLATE.md` records this key being scraped from a compromised EC2
instance twice, both times generating unexpected charges. So: use a key issued
for this project alone, and add the variable to the env var table and the
fresh-instance deploy steps in that file, so a rebuild does not come up with
the feature silently broken.

The server action calls `requireTeacher()` first, matching every write in
`app/actions.ts`. Without it this is an unauthenticated endpoint that spends
money on the project's API key.

## Testing

The vitest suite covers pure logic only; there is no React Testing Library
setup and no HTTP mocking layer, and adding either is a larger change than this
feature warrants. The two pure units carry the logic that can be wrong:

`inline-markup` — bold, italic, and code spans parse; markers mixed in one
string; an unmatched marker renders literally; an empty string yields nothing.

`card-suggestions` — the five generated fields are set from the suggestion;
date, subject, usage, englishPrompt, and frenchAnswer pass through unchanged.

No test makes a live API call.

Everything else is verified with `npm run lint`, `npm run typecheck`,
`npm test`, `npm run build`, and by running the app.

Manual checks that matter:

1. `/admin` with no card for today opens in compose; Generate is disabled until
   all three fields are filled; the editor appears populated after generating.
2. Saving, then reloading, opens directly in the editing stage with the stored
   values — no compose step, no second API call.
3. Reloading mid-compose without saving returns to compose and allows a fresh
   generation.
4. A generated card renders on `/g/[slug]` with bold, italics, and chips —
   no literal asterisks or backticks anywhere.
5. Pronunciation renders as prose with inline chips, not one chip around the
   whole field.
6. `/admin/[slug]` behaves identically.
7. With `ANTHROPIC_API_KEY` unset, Generate reports configuration trouble and
   leaves the typed fields in place.

## Out of scope

No regenerate button, no per-field regeneration, no preview toggle for the
markup, no streaming, no storing of prompts or responses, no usage metering.
Each is reasonable to want later; none is needed to find out whether the
generated cards are good enough to use.
